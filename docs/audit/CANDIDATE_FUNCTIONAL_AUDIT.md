# Candidate Functional Audit

Priority: P0 = Critical, P1 = High, P2 = Medium, P3 = Low.

| ID | Feature | Current Behavior | Problem | Evidence | Expected Behavior | Priority | Acceptance Criteria |
|---|---|---|---|---|---|---|---|
| FUNC-001 | Registration | Candidate registration submits email/password/role, backend creates pending user and candidate profile, and returns no token until email verification. | Password rules are enforced only by backend error; frontend copy says minimum 8 chars with upper/lower/digit but does not validate all rules before submit. | `frontend/src/App.tsx:1472-1597`, `backend/src/main/java/com/sjp/recruitment/service/AuthService.java:63-83`, `AuthService.java:292-298`. | Frontend and backend validation should match before submit. | P2 | Invalid password shows inline rule-specific feedback before API call and backend rejects the same constraints. |
| FUNC-002 | Login | Login stores JWT/user and redirects by role. | Logout endpoint is no-op and password change/deactivation do not invalidate existing JWTs, so old tokens remain valid until expiry. | `backend/src/main/java/com/sjp/recruitment/controller/AuthController.java:57-59`, `AuthService.java:240-251`, `frontend/src/services/api.ts:13-45`. | Logout and sensitive account changes should invalidate active tokens or use short-lived access plus revocation/refresh strategy. | P1 | After password change/deactivation/logout, old token requests to protected candidate APIs fail. |
| FUNC-003 | Forgot/reset password | Forgot password creates hashed token and emails reset link; reset validates token and password strength. | No frontend reset token precheck; reset form allows submit with missing token until backend failure. | `frontend/src/App.tsx:1691-1778`, `backend/src/main/java/com/sjp/recruitment/service/AuthService.java:132-160`. | Reset page should detect missing token and block submit with clear recovery path. | P2 | Direct `/reset-password` without token shows invalid link state and link to forgot password. |
| FUNC-004 | Protected candidate routes | `Protected` checks local stored role; backend restricts candidate APIs. | Frontend protection depends on local storage for route gating, so stale role/token can briefly render until API fails. | `frontend/src/App.tsx:811-823`, `backend/src/main/java/com/sjp/recruitment/config/SecurityConfig.java:52-53`. | Protected shell should verify current user when session age/role is uncertain. | P2 | Direct URL with stale token/role redirects after `/auth/me` validation without rendering sensitive candidate data. |
| FUNC-005 | Candidate profile | Candidate can update full name, phone, DOB, location, skills, bio, education, work experience, projects, certifications. | Backend accepts generic JSON/object arrays and unconstrained strings; no required/length/date/URL/business validations. | `frontend/src/App.tsx:2833-3049`, `backend/src/main/java/com/sjp/recruitment/model/dto/request/CandidateProfileRequest.java:7-16`, `CandidateService.java:65-78`. | Profile fields should have justified requiredness, structured section schemas, length limits, and frontend/backend parity. | P1 | Invalid DOB, overlong text, empty section titles, malformed URLs, duplicate skills, and inconsistent JSON are rejected consistently. |
| FUNC-006 | Profile recovery | Profile edits are local state and saved by button. | There is no unsaved-change guard; refresh/back/direct navigation loses edits. | `frontend/src/App.tsx:2834-2854`, no `beforeunload` or dirty-state guard found in candidate profile code. | Warn candidate before losing unsaved profile changes. | P2 | Navigating away with dirty profile state prompts confirmation or saves draft. |
| FUNC-007 | CV upload | Frontend and backend allow PDF up to 5 MB; backend stores uploaded CV and sets first as default. | File validation depends on extension and content type; no server-side PDF magic/signature validation or malware scanning. | `frontend/src/App.tsx:345-352`, `backend/src/main/java/com/sjp/recruitment/service/CandidateService.java:337-351`. | Backend should verify actual PDF content and scan/contain uploaded documents. | P1 | Non-PDF renamed as `.pdf` is rejected; infected or active-content PDFs are handled according to policy. |
| FUNC-008 | CV management | Candidate can upload, download, set default, delete uploaded CVs and create/update/delete builder CV versions. | CV builder creates snapshots from profile but profile fields are generic/unvalidated; candidate cannot inspect which exact builder version snapshot will be used from application history beyond title. | `frontend/src/App.tsx:3329-3618`, `CandidateService.java:182-211`, `ApplicationService.java:91-104`. | Application detail should expose immutable submitted CV snapshot/version clearly. | P2 | Application detail shows uploaded file or builder snapshot used at submission, including timestamp/version. |
| FUNC-009 | Job discovery | Public job list supports search/location/skills/salary/experience/sort/page with URL params and server-side pagination. | Category exists in API/service type but is not exposed in the candidate filter UI. | `frontend/src/types/job.ts:58-66`, `frontend/src/App.tsx:1963-2061`, `backend/src/main/java/com/sjp/recruitment/service/JobService.java:871-958`. | Candidate UI should expose supported category filtering or remove unused contract. | P2 | Candidate can filter by category and URL persists category, or API/types omit category for candidate search. |
| FUNC-010 | Search empty/no results | Job list renders empty state when no jobs. | Search is form-submit based, not debounced; acceptable for submit search, but no loading skeleton and error recovery is generic. | `frontend/src/App.tsx:1918-1931`, `2077-2123`. | Candidate should see clear loading/error/retry states for slow or failed search. | P2 | API failure shows retry and preserves filters; slow search shows skeleton or progress. |
| FUNC-011 | Pagination | Public jobs paginate and reset to page 0 on filter submit. | Saved jobs, applications, notifications, recommendations, CVs, and AI sessions are unpaged or hide backend pagination from UI. | `frontend/src/App.tsx:3625-4155`, `candidateService.ts:20-100`, `ApplicationService.java:141`, `CandidateService.java:213-249`, `AiInterviewService.java:209-219`. | Candidate list features should paginate or intentionally cap with "view more". | P1 | Large saved/application/notification/session datasets remain usable and do not return unbounded lists. |
| FUNC-012 | Job detail | Detail displays job info, company summary, save/apply/report actions. | Company profile is only embedded summary; there is no candidate route to a company detail page despite company information scope. | `frontend/src/App.tsx:2194-2547`, `frontend/src/types/job.ts:31-50`. | Candidate should be able to inspect company details/verification when available. | P2 | Job detail links to company profile with verification, website, locations, and active jobs. |
| FUNC-013 | Saved jobs | Candidate can save/unsave from detail and view saved jobs. | Saved job list has no pagination/error state and may include deleted/expired jobs without a distinct stale/expired state if backend returns them. | `frontend/src/App.tsx:3625-3668`, `CandidateService.java:213-220`. | Saved jobs should handle expired/deleted/closed jobs and large lists. | P2 | Expired/deleted saved jobs are labeled and removable; list has paging or load more. |
| FUNC-014 | Application submit | Backend requires apply-ready profile, active job, unique application, and owned CV/builder CV. | Frontend collects AI-consent and accuracy agreement but does not send them to backend; server has no consent fields. | `frontend/src/App.tsx:337-389`, `539-544`, `candidateService.ts:65-79`, `ApplicationSubmitRequest.java:6-10`. | Consent/acknowledgement should either be persisted/audited or removed from blocking submit. | P1 | Submitted application records candidate consent version/timestamp when consent gates submission. |
| FUNC-015 | Application duplicate | Backend rejects duplicate application. | Frontend optimistic state handles success but duplicate/race/API failure recovery is generic. | `ApplicationService.java:85-86`, `frontend/src/App.tsx:2255-2279`. | Duplicate apply should show already-applied state and route to existing application. | P2 | Duplicate response updates UI to applied and links to application detail. |
| FUNC-016 | Application tracking | Candidate list/detail shows applications, timeline, interviews, offers, and submission data. | Application list is unpaged and table/mobile card behavior needs manual verification; list fetch has no visible error state. | `frontend/src/App.tsx:3675-3976`, `ApplicationService.java:139-155`. | Candidate can recover from failed/slow application fetch and large history. | P2 | Applications page has retry/error state and pagination/search or reasonable cap. |
| FUNC-017 | Interview schedule response | Candidate can confirm, request reschedule, and respond to offers. | Response status values are free strings on frontend service; backend contract needs enum validation verification in workflow controller/service. | `frontend/src/services/candidateService.ts:102-113`, `frontend/src/App.tsx:3767-3809`. | Candidate response/offer response values should be enum-constrained across UI/API/backend. | P2 | Invalid response status cannot be sent from UI or accepted by API. |
| FUNC-018 | Notifications | Candidate can list notifications, mark one or all read; dashboard/menu uses unread count. | Notification list is unpaged and mark-read action has no failure recovery beyond reload. | `frontend/src/App.tsx:4051-4155`, `CandidateService.java:245-266`. | Notifications should paginate and show retry/error on failed mark read. | P2 | Large notification lists load incrementally; failed mark-read shows retry. |
| FUNC-019 | AI interview availability | Backend returns config status; frontend shows disabled message when AI is not configured/enabled. | UI does not show feature limit/quota details before creating a session; backend consumes feature limits after session creation. | `frontend/src/App.tsx:4561-4578`, `AiInterviewService.java:120-145`, `150-207`. | Candidate should know quota/limit before attempting expensive AI session creation. | P2 | Create buttons show remaining sessions or clear limit messaging before API failure. |
| FUNC-020 | AI interview resume/refresh | Session data is persisted; candidate can reopen a session. | Unsaved recording/transcript in current question is local state and lost on refresh/back; no draft persistence warning. | `frontend/src/App.tsx:4764-4779`, `4821-4879`. | Candidate should not lose a recorded/transcribed answer without warning or draft save. | P1 | Refresh/back during nonempty transcript prompts warning or saves draft server-side. |
| FUNC-021 | AI answer mapping | Backend requires question ID belongs to session and answer uniqueness per session/question. | Current-question audio transcription endpoint transcribes only the first unanswered question; if UI is stale, candidate may transcribe against a different current question than displayed after concurrent tab/device use. | `AiInterviewService.java:234-252`, `708-733`, schema `V1__initial_schema.sql:312-313`. | Audio upload should include expected question ID or concurrency token. | P1 | Upload audio for stale/current mismatch returns conflict instead of attaching transcript to a different question. |
| FUNC-022 | AI finish rules | Backend requires at least one non-skipped answer before finish and evaluates pending answers. | Candidate can skip all but then finish fails; UI communicates only after backend error. | `AiInterviewService.java:299-302`, `frontend/src/App.tsx:4884-4893`, `5096-5099`. | UI should make completion rules explicit and block impossible finish states. | P2 | Finish disabled or explanatory when there are no evaluable answers. |
| FUNC-023 | AI fallback feedback | Provider failures save fallback score/feedback and mark answer/session completed. | Fallback can be mistaken for real AI evaluation; score is word-count based and not grounded in rubric. | `AiInterviewService.java:345-363`, `564-585`, `frontend/src/App.tsx:4958-4965`, `5160-5168`. | Fallback should be clearly non-evaluative or exclude numeric scoring until provider evaluation succeeds. | P1 | Fallback state cannot be confused with evaluated score; retry path is prominent. |
| FUNC-024 | Speech-to-text | Backend validates audio size/duration/header and uses Gladia. | STT language config is Vietnamese-only; quality standard requires Vietnamese-English code-switching consideration. | `GladiaTranscriptionClient.java:57-60`, quality standard `docs/quality/CANDIDATE_SYSTEM_QUALITY_STANDARD.md` section 16. | STT config/benchmark should support technical English terms and mixed Vietnamese-English. | P1 | STT benchmark covers mixed-language technical answers; config supports expected languages. |
