# Candidate UX Behavior Audit

Scope: Candidate application behavior, navigation, URL state, pagination, search, filters, sorting, tabs, tables/lists, forms, dialogs, async feedback, destructive actions, responsive interaction, and consistency.

This audit does not evaluate visual attractiveness and does not modify code.

Reviewed files include:

- `frontend/src/App.tsx`
- `frontend/src/styles/global.css`
- `frontend/src/services/candidateService.ts`
- `frontend/src/services/jobService.ts`
- `frontend/src/services/aiInterviewService.ts`
- `frontend/src/pages/billing/SubscriptionPlansPage.tsx`
- `frontend/src/pages/billing/PaymentCheckoutPage.tsx`
- `frontend/src/pages/billing/PaymentResultPage.tsx`
- `frontend/src/pages/billing/BankTransferCheckoutPage.tsx`
- Candidate backend list/search endpoints for pagination behavior

## Behavioral Summary

The Candidate app behaves like a partially mature modern web app. The public job search flow is the strongest area: search filters and page are URL-backed, browser Back from a job detail normally returns to the same search URL, and server-side pagination is used. Candidate-owned areas are less mature: several lists are unpaged, many async failures have no recoverable UI, forms often use global messages instead of field-level errors, and modal behavior lacks focus/Escape handling.

Specific Back behavior asked in the prompt: if a Candidate opens a job detail from page 4 of search results, then presses browser Back, the URL should return to `/jobs?...&page=3` because job cards use normal `Link` navigation and search/page state is encoded in query params. The app will re-read the filters/page from `useSearchParams`. The main caveat is scroll restoration: there is no explicit React Router scroll restoration, and `changePage` always scrolls to top, so the Candidate may not return to the same scroll position within page 4.

## URL State Inventory

| Screen/component | Current URL state | Should be URL state? | Assessment |
|---|---|---|---|
| Home job search | Redirects to `/jobs?search=...` | Yes | Good for sharing/search continuation. |
| Jobs page | `search`, `location`, `skills`, `experienceLevel`, `minSalary`, `maxSalary`, `sort`, `page` | Yes | Mostly good; category exists in API/types but is not restored from URL. |
| Job detail | Job id in path | Yes | Good direct URL support, but no query/back context link. |
| Candidate profile/account/CVs | Route only | Mostly no | Draft form state should be guarded or locally persisted, not necessarily in URL. |
| Saved jobs/applications/notifications | Route only | Page/search/filter should be URL state once pagination/filtering exists | Current lists are unpaged and not deep-linkable beyond route. |
| Application detail | Application id in path | Yes | Direct access works; return path is fixed to applications list. |
| AI interview tabs | Local `activeTab`, `questionMode`, selected session | Yes for tab/mode/session | Refresh/back loses selected tab/mode/session context. |
| Subscription plans/payment | Plan/payment ids in URL | Yes | Payment flow uses URL state appropriately. |

| Route | List | Pagination required? | Current behavior | Assessment |
|---|---|---|---|---|

| `/candidate/subscription/plans` | Plan catalog | No | Loads all plans | Acceptable because catalog should remain small. |

## Recommended URL State

Use URL state where it improves refresh, sharing, and Back:

- `/jobs`: keep `search`, `location`, `skills`, `minSalary`, `maxSalary`, `experienceLevel`, `category`, `jobType`, `workMode`, `sort`, `page`.
- `/candidate/applications`: add `page`, `status`, `search`, optionally `sort`.
- `/candidate/saved-jobs`: add `page`, optionally `search` or `status` if expired/closed filtering is introduced.
- `/candidate/notifications`: add `page` and optionally `unread=true`.
- `/candidate/ai-interviews`: add `tab`, `mode`, `sessionId`, optionally `page`.
- Do not put ordinary profile form draft fields in the URL; use dirty guards or local draft persistence instead.

## Positive Behaviors To Preserve

- Job search uses URL-backed filters/page and server-side pagination.
- Search filter submit resets page to 0, which is appropriate.
- Job cards use real links, so browser Back and open-in-new-tab behavior work.
- Apply modal uses a real form submit, disables duplicate submit while busy, and has keyboard activation on the upload drop zone.
- CV deletion has confirmation dialogs.
- Payment routes carry payment/plan ids in URLs, which supports refresh and direct recovery.
